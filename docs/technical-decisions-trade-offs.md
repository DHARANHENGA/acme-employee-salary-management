# Technical Decisions & Trade-offs

## 1. Purpose

This document records the major technical decisions made during the design and development of the ACME Employee Salary Management application.

Each decision includes the selected approach, alternatives considered, and the reasoning behind the decision.

---

## 2. Frontend Architecture

### Decision

Use a **component-based React architecture** with a lightweight separation of:

- Pages
- Reusable components
- Services
- API client
- Assets

### Alternatives Considered

- MVVM
- Feature-based architecture
- Component-based architecture

### Trade-off

MVVM provides a strong separation between view, view-model and model, but introduces additional abstraction that is unnecessary for the small number of screens in this application.

Feature-based architecture is useful for larger applications with many independent business domains, but would introduce unnecessary complexity for this assessment.

### Selected Approach

Component-based architecture provides sufficient separation while keeping the application simple and maintainable.

---

## 3. Backend Architecture

### Decision

Use a layered backend architecture:

```text
Router
   ↓
Controller
   ↓
Service
   ↓
Repository
   ↓
Database
```

### Responsibilities

**Router**
- Defines API endpoints.
- Maps requests to controllers.

**Controller**
- Handles HTTP requests and responses.
- Passes operations to services.

**Service**
- Contains business logic.
- Performs salary analytics calculations.
- Handles currency conversion.
- Coordinates repository operations.

**Repository**
- Handles database access.
- Keeps database-specific logic isolated from business logic.

### Trade-off

A simpler approach could place business logic and database queries directly inside controllers.

The layered approach provides better separation of concerns, testability and maintainability.

---

## 4. Database Access

### Decision

Use **Prisma ORM** for database access.

### Alternative

Raw SQL.

### Trade-off

**Prisma**

- Type-safe database access.
- Strong TypeScript integration.
- Less boilerplate.
- Easier schema management and maintenance.

**Raw SQL**

- Provides complete control over SQL queries.
- Useful for highly complex or heavily optimized queries.
- Requires more boilerplate and manual handling.

### Selected Approach

Prisma provides the appropriate balance between type safety, productivity and maintainability for this application.

---

## 5. Employee Identifier

### Decision

Use two identifiers:

```text
id
employeeId
```

`id` is the internal database primary key.

`employeeId` is the business identifier exposed through the API.

Example:

```text
EMP-00123
```

### Reason

Keeping the database identifier separate from the business identifier prevents internal database implementation details from becoming part of the external API contract.

The `employeeId` is generated by the backend when an employee is created.

---

## 6. Analytics Calculation

### Decision

All salary analytics calculations are performed by the backend.

The backend calculates:

- Total payroll
- Average salary
- Median salary
- Employee count
- Salary by country
- Salary by department
- Salary bands
- Percentage distribution

### Alternative

Perform calculations in the frontend after retrieving employee records.

### Trade-off

Frontend calculations would require transferring potentially large datasets and duplicate business logic in the client.

Backend calculation:

- Reduces data transferred to the frontend.
- Keeps business logic centralized.
- Prevents inconsistent calculations.
- Allows the frontend to focus on presentation.

### Selected Approach

The frontend only binds and displays values returned by the backend.

---

## 7. Analytics API Design

### Decision

Use a single analytics endpoint:

```http
GET /api/analytics
```

Optional filters can be supplied:

```http
GET /api/analytics?countryId=1
```

```http
GET /api/analytics?departmentId=2
```

```http
GET /api/analytics?countryId=1&departmentId=2
```

### Alternative

Create separate endpoints:

```text
GET /api/analytics/summary
GET /api/analytics/country
GET /api/analytics/department
GET /api/analytics/salary-bands
```

### Trade-off

Multiple endpoints would require multiple frontend requests to populate a single analytics screen.

A single endpoint allows the analytics screen to retrieve the complete analytics dataset in one request.

### Selected Approach

Use one analytics endpoint with optional filters.

---

## 8. Employee Details API

### Decision

Do not provide a separate:

```http
GET /api/employees/{employeeId}
```

endpoint.

### Reason

The employee grid already retrieves the information required by the edit modal.

When the user selects **Edit**, the existing employee row can be passed to the edit form.

This avoids an unnecessary API request.

### Trade-off

If the edit screen eventually requires information that is not available in the employee grid, a dedicated details endpoint can be introduced later.

---

## 9. Employee Deactivation

### Decision

Use soft deactivation instead of permanently deleting employee records.

Endpoint:

```http
PATCH /api/employees/{employeeId}/deactivate
```

The employee remains in the database with:

```text
status = INACTIVE
```

### Alternative

Hard delete the employee record.

### Trade-off

Hard deletion permanently removes historical information.

Soft deactivation preserves employee history and allows organizational analytics to remain historically accurate.

---

## 10. Validation

### Decision

Use **Zod** for request validation.

Validation is performed on both:

- Frontend
- Backend

### Trade-off

Frontend validation provides immediate feedback to users.

Backend validation remains mandatory because frontend validation cannot be trusted as the authoritative validation layer.

---

## 11. Error Handling

### Decision

Use centralized error handling on the backend.

All APIs follow a consistent response structure:

```json
{
  "status": "success",
  "code": "EMPLOYEE_CREATED",
  "message": "Employee created successfully",
  "data": {}
}
```

Errors follow the same structure:

```json
{
  "status": "error",
  "code": "VALIDATION_ERROR",
  "message": "Request validation failed",
  "data": {}
}
```

The frontend handles API errors and displays appropriate user-facing messages.

A dedicated error-log database table is not required for this assessment.

---

## 12. Pagination and Filtering

### Decision

Pagination and filtering are handled by the backend.

Example:

```http
GET /api/employees?page=1&limit=20
```

Filtering can be combined:

```http
GET /api/employees?departmentId=2&countryId=1&status=ACTIVE
```

### Reason

The application contains approximately 10,000 employees.

Retrieving the complete dataset and filtering it in the frontend would be inefficient.

The backend performs filtering and pagination before returning the response.

---

## 13. Seed Data

### Decision

Generate approximately **10,000 employee records** using a database seed script.

### Alternative

Maintain 10,000 manually created JSON records.

### Trade-off

A generated seed script is:

- Reproducible.
- Easier to maintain.
- Easier to modify.
- Suitable for resetting development data.

Reference data will also be populated through the seed process.

---

## 14. API Response Design

### Decision

All APIs use a consistent response envelope:

```text
status
code
message
data
```

Paginated responses additionally contain:

```text
pagination
```

Example:

```json
{
  "status": "success",
  "code": "EMPLOYEE_UPDATED",
  "message": "Employee updated successfully",
  "data": null
}
```

### Reason

A consistent response structure simplifies frontend API handling and makes the API predictable.

---

## 15. Frontend Data Responsibility

### Decision

The frontend should **not perform business calculations or salary derivations**.

The frontend is responsible for:

- Fetching data.
- Binding API responses.
- Rendering tables.
- Rendering charts.
- Handling user interactions.
- Sending user input to APIs.
- Displaying validation and API errors.

The backend is responsible for:

- Salary calculations.
- Currency conversion.
- Analytics calculations.
- Filtering.
- Pagination.
- Business validation.

### Reason

This maintains a clear separation between presentation logic and business logic.

---

## 16. Decision Summary

| Area | Selected Decision |
|---|---|
| Frontend | Component-based React architecture |
| Backend | Router → Controller → Service → Repository |
| Database ORM | Prisma |
| Employee ID | Backend-generated business identifier |
| Analytics | Backend calculated |
| Analytics API | Single endpoint with filters |
| Employee Details API | Not required |
| Employee Deletion | Soft deactivation |
| Validation | Zod |
| Error Handling | Centralized error handling |
| Error Log Table | Not required |
| Pagination | Backend |
| Filtering | Backend |
| Seed Data | Script-generated 10,000 employees |
| Frontend Calculations | Not allowed |
| API Response | `status`, `code`, `message`, `data` |

---

## 17. Conclusion

The selected architecture prioritizes simplicity, maintainability and clear separation of responsibilities while avoiding unnecessary complexity for the scope of the assessment.

These decisions can be revisited if the application requirements grow beyond the current scope.
